# Completed Task History backfill

Deploy the Function App write changes before running the backfill. Keep the new client view disabled until the backfill has completed and its report has been reviewed. The operation reads the existing Cosmos DB `xp-event` and `routine-transition` history in pages of 100 items and never reads current Notion project assignments for legacy completions.

The maintenance endpoint is `POST /api/task-xp/{TaskXp:ReadRouteSegment}/completed-task-backfill?mode=dry-run` or `?mode=apply`. It requires an Azure Functions function key in addition to the route segment. Keep both values out of logs and shared reports. Run `dry-run` first against representative legacy data and save its JSON response securely. The report includes candidate and existing snapshot counts, skipped or ambiguous event IDs and reasons, later-day XP adjustment counts, and the largest projected period item size in bytes. Review skipped cases individually; the operation does not infer a completion or change XP for them.

Run `apply` only after reviewing the dry-run report and verifying that projected month items and the transactional batch request will remain below the Cosmos DB 2 MB limits. Before changing a candidate, the operation rereads its current award and revoke history. It conditionally replaces the task state or routine occurrence by ETag in the same partition batch as the day, week, and month documents. A concurrent correction makes the batch retry against current history, so an invalidated same-day completion is removed or skipped. Historic later-day revocations receive separate `completion-backfill-adjustment:{revokeEventId}` markers in the same batch as their all-time and reopening-period XP corrections. Original XP events are preserved. Before writing the final `completed-task-backfill:latest` marker, the operation reconciles every candidate against current history across all three snapshot periods and verifies adjustment markers.

If the call is interrupted, run `dry-run` again, inspect its report, then rerun `apply`. Snapshot IDs and adjustment markers make repeat runs idempotent. The expected migration contains only a few dozen documents, so a single scan is appropriate; it has no scan checkpoint. Do not infer completion metadata from current Notion pages. Keep a copy of the report, including any possible XP-to-snapshot discrepancies for skipped cases. Verify several old day, week, and month responses and the year XP-only response before enabling the client view. Rerun `apply` once to confirm that it creates no duplicate snapshots or XP adjustments.

The implementation does not automatically run this migration during startup or deployment. Application code alone cannot verify historic data or safely apply corrections without access to the target Cosmos DB environment.
